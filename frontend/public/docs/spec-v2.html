1.리마스터 배경 및 목표

원본 팀 프로젝트는 팀 계정 인프라(Supabase 등)에 접근할 수 없게 되면서 서비스가 중단된 상태였습니다. 리마스터는 원본 코드 스냅샷에서 새로 시작해 ① 개인 계정 무료 인프라로의 완전 이전, ② 외부 미디어 SaaS 의존 제거, ③ 클라이언트 신뢰 기반 구조의 보안 재설계, ④ 게임 규칙 개편(3~6인)을 목표로 진행했습니다.

v1 한계v2 목표 (달성 상태)
LiveKit Cloud 의존순수 WebRTC P2P mesh 전환 — 외부 미디어 서버 0대 (완료)
최소 5인 필요(5~10인) · 의사는 8인 이상에서만 배정3~6인 · 인원별 역할 분배 개편 — WebRTC mesh 상한 6인 반영 (완료)
클라이언트가 계정 생성 · 점수 갱신 · role 조회RLS + 컬럼 차단 + service_role 서버 단독 쓰기 (완료)
게임 시작 검증 부재방장 검증 + 게임 루프 중복 실행 차단 (완료)
유료 · 접근 불가 인프라Vercel + Render free + Supabase 무료 티어 (완료)

4.기능 명세

4.1 인증 (FR-1xx)

FR-101 이메일 회원가입

  • 이메일 형식 검사 후 [중복확인] 버튼으로 account_table 등록 여부를 조회합니다.
  • 닉네임은 2~6자(영문 · 한글 · 숫자), 비밀번호는 6~20자로 제한하며 확인 입력과의 일치를 검사합니다.
  • 4개 항목이 모두 통과해야 [회원가입] 버튼이 활성화됩니다. 항목별 통과 여부를 실시간 메시지로 안내합니다.
  • 계정 행은 클라이언트가 아니라 DB 트리거 handle_new_user가 자동 생성합니다 (§6.3).

FR-102 이메일 로그인

  • 이메일 + 비밀번호로 로그인하며, [이메일 저장] 선택 시 쿠키에 30일간 보관합니다.
  • 실패 시 원인별 에러 메시지를 폼 하단에 표시합니다.

FR-103 소셜 로그인 (카카오 · 구글)

  • Supabase OAuth Provider를 경유하며, 콜백은 /sns-login에서 세션 확인 후 로비로 이동합니다.
  • 간편가입 시에도 계정 행은 동일하게 DB 트리거가 생성합니다 (닉네임은 소셜 프로필 → 이메일 로컬파트 순 fallback).
  • 깃허브 · 페이스북은 v2에서 제거했습니다 (§10 참조).

FR-104 세션 관리 · 접근 제어

  • 미들웨어가 모든 요청에서 Supabase 세션을 갱신합니다.
  • 로그인 상태로 인트로 · 로그인 · 회원가입 페이지 접근 시 로비로 리다이렉트합니다.
  • 방 만들기 · 입장 등 게임 기능은 비로그인 시 토스트로 안내하고 차단합니다.

4.2 로비 · 방 관리 (FR-2xx)

FR-201 방 목록

  • 방 카드에 제목 · 게임 카테고리 해시태그 · 현재인원/총인원 · [입장하기] 버튼을 표시합니다.
  • 게임 중인 방은 입장 버튼 대신 "playing..."을 표시하고 입장을 차단합니다.
  • 서버가 방 정보 변경을 브로드캐스트할 때마다 목록을 재조회하여 실시간 동기화합니다.
  • 목록 로딩 전에는 스켈레톤 UI를 표시합니다.

FR-202 방 검색

  • 제목 부분 일치 검색을 500ms 디바운스로 수행합니다.
  • 검색어를 비우면 전체 목록을 다시 요청합니다.

FR-203 방 만들기

  • 방 제목은 필수이며 최대 16자입니다.
  • 인원수는 3~6명 중 선택합니다. 상한 · 하한은 shared/constants.ts가 FE 모달과 BE 검증의 단일 소스입니다.
  • 서버도 인원수를 재검증하여 3~6 범위 밖 요청을 거부합니다.
  • 생성 성공 시 곧바로 해당 방에 입장 처리되어 /room/{id}로 이동합니다.
  • 게임 선택지 중 "노래맞추기"는 준비 중 안내만 표시합니다 (§8).

FR-204 입장 경로 3종

  • ① 방 목록 [입장하기] ② 로비 상단 [빠른입장] ③ 슬라이드 [Game Start] (②와 동일 동작)를 제공합니다.
  • 빠른입장은 총원 오름차순 → 현재원 내림차순으로 정렬해 자리가 남은 첫 방에 배정하고, 없으면 실패를 안내합니다.
  • 공통 입장 거부 조건: 만석 / 동일 유저 중복 입장 / 게임 진행 중.

FR-205 방장 자동 지정 · 위임

  • 입장 시각(join_time)이 가장 빠른 유저를 방장으로 지정합니다.
  • 입장 · 퇴장이 발생할 때마다 재계산되어 방장이 나가면 다음 유저에게 자동 위임됩니다.

FR-206 퇴장 처리

  • [방 나가기] 버튼, 브라우저 뒤로가기(popstate 감지), 소켓 연결 끊김 모두 퇴장으로 처리합니다.
  • 캠 · 마이크 트랙이 종료되면(기기 분리 · 권한 회수) 강제 퇴장합니다.
  • 입장 전 새로고침 · 이탈 시도 시 확인창을 표시합니다.
  • 마지막 1인이 나가면 방을 삭제합니다 (매칭 행은 FK cascade로 함께 삭제).

FR-207 준비 / 게임 시작

  • 참가자는 [게임 준비] ↔ [취소]를 토글합니다.
  • 정원 충족 + 전원 준비 완료 시 방장에게만 시작 권한이 부여되어 버튼이 [게임시작]으로 전환됩니다.
  • 시작 요청 시 서버가 3중 검증합니다: ① 게임 루프 중복 실행 차단(레지스트리) ② 요청자가 방장인지 소켓 데이터로 확인 ③ 인원수를 클라이언트 값 대신 DB 기준으로 재확인.

4.3 게임 진행 (FR-3xx)

FR-301 사회자 자동 진행 (게임 루프)

  • 서버가 1초 간격 스테이트 머신으로 전 단계를 자동 진행합니다. 단계 전환 · 안내 모달 · 타이머 · 캠/마이크 제어를 모두 서버가 지시합니다.
  • 라운드 타임라인 상세는 §5.2를 따릅니다.
  • 어느 단계에서든 오류 발생 시 게임 상태를 초기화하고 방을 대기 상태로 되돌립니다.

FR-302 역할 배정

  • 게임 시작 시 전원을 시민으로 초기화한 뒤, 셔플된 순서로 마피아 → 의사 → 경찰을 배정합니다 (§5.1 분배표).
  • 각자 자신의 직업 카드를 모달로 확인하며, 마피아끼리는 밤 0에 캠으로 서로를 확인합니다.
  • 화면 구석 툴팁에 본인 직업 아이콘 · 설명을 상시 표시합니다.

FR-303 낮 토론 · 지목 투표

  • 낮이 되면 생존자 전원의 캠 · 마이크가 켜지고 60초간 토론합니다.
  • 토론 종료 후 10초간 의심 대상의 캠을 클릭해 투표합니다. 사망자는 투표할 수 없고 투표 대상도 되지 않습니다.
  • 득표 결과를 모달로 공개합니다. 최다득표 동률 처리는 §5.3을 따릅니다.

FR-304 최후의 변론 · 찬반 투표

  • 최다득표자만 캠 · 마이크가 켜져 10초간 변론합니다.
  • 이후 10초간 처형 찬반 투표를 진행합니다. 대상자 본인과 사망자는 투표할 수 없습니다.
  • 찬성이 반대보다 많으면 처형하고, 처형자의 소속(마피아/시민)을 공개합니다. 그 외에는 아무도 죽지 않습니다.

FR-305 밤 행동 (마피아 · 의사 · 경찰)

  • 마피아: 생존 마피아끼리만 캠이 켜진 상태로 10초간 제거 대상의 캠을 클릭합니다 (음성 없이 제스처로 상의).
  • 의사: 10초간 보호할 대상을 선택합니다.
  • 경찰: 10초간 조사 대상을 선택하면 그 직업이 화면에 표시됩니다.
  • 인원 구성상 존재하지 않는 직업의 단계는 건너뜁니다.

FR-306 밤 결과 정산 · 승리 판정

  • 마피아 최다 지목 대상이 의사의 보호 대상과 다르면 사망 처리합니다. 보호에 성공하면 마피아에게만 별도 문구로 안내합니다.
  • 매 tick마다 승리 조건을 검사합니다: 생존 마피아 0명 → 시민 승 / 생존 마피아 ≥ 생존 시민 → 마피아 승.
  • 승리 시 승리 팀 · 승자 목록을 폭죽 연출과 함께 표시하고, 게임 상태를 초기화한 뒤 로비 목록을 갱신합니다.

FR-307 플레이어 번호 · 사망 표시

  • 모든 클라이언트가 join_time → user_id 정렬로 동일한 플레이어 번호를 계산합니다.
  • 사망자 캠에는 사망 오버레이를 표시하며, 모든 선택 단계에서 클릭이 비활성화됩니다.

4.4 화상 · 음성 (FR-4xx)

FR-401 입장 전 캠 · 마이크 설정

  • 방 진입 시 캠 · 마이크 권한을 요청하고 좌우반전 미리보기를 표시합니다. [입장하기]를 눌러야 실제 참여합니다.
  • 권한 거부 · 장치 오류 시 전용 안내 화면으로 전환합니다 — Windows/Mac별 OS 설정 경로, 브라우저 업데이트, 백신 · VPN 확인 등 트러블슈팅과 [메인페이지로 이동하기]를 제공합니다.

FR-402 WebRTC P2P mesh 연결

  • 참가자 전원이 1:1로 연결되는 full mesh 구조입니다 (최대 6인 — 인원 상한의 근거).
  • 시그널링은 별도 서버 없이 기존 Socket.IO 게임 서버가 SDP · ICE를 릴레이합니다.
  • 동시 offer 충돌(glare)은 userId 사전순으로 작은 쪽만 offer를 발신하는 규칙으로 방지합니다.
  • 원격 설명(remoteDescription) 설정 전에 도착한 ICE candidate는 큐에 보관했다가 일괄 적용합니다.
  • ICE 서버는 Google 공개 STUN을 기본으로 하고, TURN은 환경변수로 선택 주입합니다.

FR-403 서버 제어 미디어 on/off

  • 서버가 게임 단계에 따라 유저별 { 캠, 마이크 } 상태 맵을 내려보냅니다.
  • 본인은 송출 트랙 자체를 켜고 끄며, 상대는 수신 트랙의 로컬 재생을 제어합니다.
  • 게임 종료 · 오류 시 전체 트랙을 원상 복구합니다. 로컬 영상은 음소거로 하울링을 방지합니다.

FR-404 연결 수명 관리

  • 연결 상태가 failed · closed가 되면 해당 peer를 정리합니다.
  • 방 명단에서 사라진 유저의 peer 연결도 자동 정리합니다.

4.5 랭킹 · 점수 (FR-5xx)

FR-501 점수 반영

  • 게임 종료 시 서버가 service_role 권한으로 일괄 갱신합니다 — 클라이언트는 점수를 쓸 수 없습니다.
  • 승리 팀 +100점, 패배 팀 +20점(참가 점수)을 마피아 점수에 더하고, 총점 = 마피아 점수 + 노래맞추기 점수로 갱신합니다.

FR-502 랭킹 페이지

  • 매 요청 최신 점수를 렌더링합니다 (force-dynamic — 기존 30분 캐시 제거).
  • 총점 내림차순, 동점자는 표준 경쟁 랭킹(1 · 2 · 2 · 4 방식)으로 표기합니다.
  • 10명 단위 페이지네이션과 1~3위 메달 스타일을 적용합니다.
  • 로그인 유저의 본인 순위를 목록 상단에 고정 표시합니다.

4.6 부가 기능 (FR-6xx)

FR-601 게임 룰 튜토리얼 (/mafiainfo)

  • 게임룸 · 기본규칙 · 낮 · 투표 · 최후의 변론 · 찬반투표 · 밤 · 승리조건 · 참가인원을 섹션별로 안내합니다.
  • 스크롤 프로그레스바와 패럴랙스 타이틀을 적용했습니다.

FR-602 공지 · 문의 · 안내

  • 로비 진입 시 "캠 · 마이크 필수" 공지 팝업을 표시하며 [하루 보지 않기]를 쿠키로 기억합니다.
  • 문의 폼(/inquiry)은 EmailJS로 발송하고 결과를 토스트로 안내합니다.
  • 로비 우하단에 서비스 QnA용 Typebot 챗봇 버블을 제공합니다.

FR-603 공통 UI · 분석

  • 반응형 내비게이션(햄버거), 최상단 이동 버튼, 스켈레톤 · 스피너 · 이탈 로딩 3종을 제공합니다.
  • GA4 페이지뷰를 라우트 변경마다 전송하되, 키 미설정 · localhost에서는 추적만 스킵하고 앱은 정상 동작합니다.

5.3 투표 · 동률 규칙

  • 지목 투표 최다득표자가 1명이면 최후의 변론으로 진행합니다.
  • 최다득표 동률이면 동률자 중 1명이 즉시 사망 처리되고 변론 · 찬반 단계를 건너뜁니다 (v1 규칙 계승 — §9 참조).
  • 찬반 투표는 찬성이 반대보다 많을 때만 처형합니다. 동수 · 반대 우세면 아무도 죽지 않습니다.

5.4 승리 판정 · 점수

  • 생존 마피아 0명 → 시민 팀 승리 / 생존 마피아 ≥ 생존 시민 → 마피아 팀 승리. 매 tick 검사하며 역할 공개 전 구간은 제외합니다.
  • 마피아 승리 시 마피아 전원이 승자, 시민 승리 시 그 외 전원이 승자입니다.
  • 승자 +100점 / 패자 +20점을 서버가 일괄 반영한 뒤 (FR-501), 게임 상태를 초기화하고 방을 대기 상태로 되돌립니다.

6.데이터 명세 및 보안 설계

6.1 테이블 구조 (Supabase Postgres · 3개)

테이블 · 컬럼설명
account_table
user_id(PK) · email · nickname · mafia_score · music_score · total_score		 계정 · 누적 점수. user_id는 Supabase Auth user id. 점수 3종은 기본값 0
room_table
room_id(PK) · title · game_category · chief · current_user_count · total_user_count · is_playing · created_at		 게임 방. chief는 방장 user_id(자동 재계산), total_user_count는 3~6, is_playing은 게임 중 난입 차단용
room_user_match_table
match_id(PK) · room_id(FK, cascade) · user_id · user_nickname · role · is_lived · is_ready · is_selected · voted_count · vote_yes_or_no · join_time · vote_time		 방-유저 매칭 + 게임 진행 상태. role은 마피아 · 시민 · 의사 · 경찰, join_time은 방장 결정 · 플레이어 번호의 기준

6.2 권한 모델 (RLS)

  • 3개 테이블 모두 RLS를 활성화하고 select 정책만 둡니다 — 쓰기 정책은 의도적으로 없어 클라이언트 쓰기가 전면 차단됩니다.
  • 모든 쓰기는 백엔드가 SUPABASE_SERVICE_ROLE_KEY로 RLS를 우회하여 수행합니다.
  • 마피아 정체 은닉 (컬럼 단위 차단): room_user_match_table에서 일반 권한의 select를 회수하고 명단 표시에 필요한 컬럼(match_id · room_id · user_id · user_nickname · is_ready · is_lived · join_time)만 재부여합니다. role과 투표 컬럼은 service_role만 조회할 수 있습니다.

6.3 계정 자동 생성 트리거

  • auth.users에 행이 생기면 트리거 handle_new_user가 account_table 행을 생성합니다 — 이메일 가입과 소셜 가입을 동일 경로로 처리합니다.
  • 닉네임은 가입 메타데이터 → 소셜 프로필 이름 → 이메일 로컬파트 순으로 fallback합니다.
적용 순서 주의: 보안 SQL은 백엔드에 service_role 키 배포가 완료된 뒤 실행해야 합니다. 역순으로 적용하면(백엔드가 anon key인 상태에서 RLS를 켜면) 게임 진행 전체가 막힙니다. supabase/security.sql은 멱등 스크립트로 재실행이 안전합니다.

8.범위 제외

다음 항목은 v2 범위에서 의도적으로 제외했으며, 코드에 자리만 있는 항목은 상태를 명시합니다.

  • 노래맞추기 게임 — 로비 슬라이드 · 방 만들기 선택지 · 랭킹 컬럼(music_score)까지 자리는 있으나 선택 시 "준비 중" 안내만 표시합니다.
  • 텍스트 채팅 — 미제공. 게임 내 소통은 화상 · 음성(및 밤의 마피아 제스처)으로만 이뤄집니다.
  • 마이페이지 · 프로필 수정 — 미제공. 닉네임 변경 API가 정의만 된 미사용 코드로 남아 있습니다.
  • 방 비밀번호(비공개 방) — 미제공.
  • 게스트(비회원) 플레이 — 미제공. 게임 이용은 로그인 필수입니다.
  • 사운드 · BGM — 효과음 · 배경음악 미제공.
  • 입장 전 장치 선택 — 캠 · 마이크 on/off와 권한 확인만 제공하며, 장치(카메라 · 마이크) 선택 드롭다운은 없습니다.

9.알려진 한계

  • 지목 투표 동률 규칙 — 동률자 중 1명이 재투표 없이 즉시 사망하는 v1 규칙을 계승했습니다. 재투표 방식 도입을 검토할 여지가 있습니다.
  • 극단 상황 엣지 케이스 — 생존자가 1명뿐인 상태의 득표 집계에서 배열 인덱스 오류 가능성이 있습니다.
  • 동시 참여 전제 — 일부 게임 상태 갱신이 방 구분 없이 user_id만으로 수행되어, 동일 유저가 두 방에 동시에 존재하지 않는다는 전제(입장 거부 조건으로 보장)에 의존합니다.
  • 룰 문서와 구현의 표기 차이 — 게임 방법 페이지에는 최후의 변론이 30초로 안내되어 있으나 구현은 10초입니다. 문서 갱신이 필요합니다.
  • Render 콜드스타트 — 무료 티어 특성상 15분 무접속 시 서버가 잠들어 첫 접속에 약 1분의 지연이 발생합니다.
